# ドキュメント生成規約

## 目的

Codex に「○○の一覧を作成して」と依頼したとき、要素の一覧ページ、リンク先の要素フォルダ、および要素に適した `README.md` を一貫した形式で作成できるようにする。

この規約は [基本設計](./01_基本設計.md) の要素階層と役割を、Markdown ファイルへ展開する際の実装規約である。

## 用語

| 用語 | 意味 |
| --- | --- |
| 要素タイプ | `Subject`、`Achievement`、`Evidence`、`Result`、`Record`、`Todo`、`Schema`、`Group` のいずれか。`Documents/<要素タイプ>/` が格納先となる。 |
| 現在のフォルダ名 | 一覧ページを持つ要素のフォルダ名。例: `FactStatusDomain_GetEntity`。 |
| 飛ぶ先のフォルダ名 | 一覧から作成・参照する子要素または関連要素を表す、半角英数字だけの名前。例: `DomainMainGetEntity`。 |
| 一覧ページ | 要素の `README.md` 内にある、子要素・関連要素へのリンクを並べた節。 |

`Document` は `Documents/README.md` をルートとし、他の要素タイプは `Documents/<要素タイプ>/<要素フォルダ名>/README.md` に配置する。

## Codex への依頼と実施範囲

依頼者は、たとえば次のように依頼する。

```text
「指定したエンティティを更新」の実装証拠の一覧を作成して
```

Codex は、依頼文と既存の親 `README.md` から、次を特定して作業する。

1. 一覧を追加する親要素と、その `README.md`
2. 作成対象の要素タイプ（この例では `Evidence`）
3. 各一覧項目の表示名と飛ぶ先のフォルダ名
4. その要素タイプに許された親子関係

一覧の項目名だけが与えられた場合は、既存の文脈から補える範囲の項目を作成する。親要素、要素タイプ、またはリンク先の意味を一意に決められない場合は、ファイルを推測で作成せず確認する。

## フォルダ名とリンクの規約

### フォルダ名

リンク先の要素フォルダ名は、現在のフォルダ名の先頭の接頭辞を 1 つ外し、次の形式とする。

```text
<現在のフォルダ名から先頭の接頭辞を除いた名前>_<飛ぶ先のフォルダ名>
```

この規則によって、上位の文脈は上位要素のフォルダ名で表現し、下位要素のフォルダ名へ同じ接頭辞を繰り返さない。飛ぶ先のフォルダ名には、日本語・空白・記号を使わず、半角英数字のみを使う。

例として、`Documents_FactStatusDomain` の `README.md` から Achievement へリンクする場合、`FactStatusDomain_GetEntity` は正しいリンク先フォルダ名である。一方、`FactStatusDomain_GetEntity` の `README.md` から Evidence へリンクする場合は、`FactStatusDomain_` を引き継がず、次のように `GetEntity_` から始める。

```text
Documents/Evidence/GetEntity_DomainMainGetEntity/README.md
```

階層を下るたびの命名例は次のとおりである。

| リンク元のフォルダ名 | リンク先の要素タイプ | リンク先のフォルダ名 | 外す接頭辞 |
| --- | --- | --- | --- |
| `Documents_FactStatusDomain` | Achievement | `FactStatusDomain_GetEntity` | `Documents_` |
| `FactStatusDomain_GetEntity` | Evidence | `GetEntity_DomainMainGetEntity` | `FactStatusDomain_` |
| `GetEntity_DomainMainGetEntity` | Result | `DomainMainGetEntity_Succeeded` | `GetEntity_` |
| `DomainMainGetEntity_Succeeded` | Record | `Succeeded_20260927103000` | `DomainMainGetEntity_` |

要素名が複数の `_` を含む場合も、リンク先に残すのは先頭の `_` より後ろの部分である。たとえば `FactStatusDomain_GetEntity` からは `GetEntity` を残す。これを「接頭辞をずらす」と呼ぶ。

### 一覧のリンク行

要素フォルダ配下の `README.md` から別の要素タイプへリンクする場合は、各項目を独立した Markdown リンク行として記載する。リンク先の相対パスは必ず次の形式にする。

```markdown
[<表示名>](../../<要素タイプ>/<接頭辞を外した現在のフォルダ名>_<飛ぶ先のフォルダ名>/README.md)  
```

実例:

```markdown
[DomainMainでEntityを取得](../../Evidence/GetEntity_DomainMainGetEntity/README.md)  
```

リンク行には末尾の半角スペースを 2 個付け、Markdown 上で一項目ずつ改行する。リンクを追加するときは、リンク先フォルダとその `README.md` も同時に作成するため、リンク切れを残さない。

`Documents/README.md` から直下の要素タイプへリンクする場合だけは、ルートからの相対パスを用いる。

```markdown
[<表示名>](./<要素タイプ>/<要素フォルダ名>/README.md)  
```

## 許可する親子関係

基本設計の階層に従い、一覧とリンク先は次の関係に限定する。

| 親要素 | 作成できる一覧の要素タイプ |
| --- | --- |
| Document | Subject、Schema、Group |
| Subject | Achievement、Schema、Group |
| Achievement | Evidence、Todo、Schema、Group |
| Evidence | Result、Todo、Schema、Group |
| Result | Record |
| Group | Subject、Achievement、Evidence、Todo、Schema（横断的な関連付け） |

`Todo`、`Schema`、`Record` は末端要素である。`Group` は親子の所属を変更せず、複数要素を横断してまとめるためのリンク集として扱う。

## README.md の記載規約

すべての要素フォルダには `README.md` を作成し、先頭を要素のタイトル（`# <タイトル>`）とする。`__*A` のひな型がある要素タイプでは、作成前に必ず当該ひな型を読み、見出しの名前・順序・リンク一覧の節をそのまま使用する。ひな型にない節を追加しない。各 `README.md` の末尾には、区切り線と親要素へ戻る `[Back](...)` リンクを置く。

| 要素タイプ | 正とする `__*A` ひな型 | 必須の内容・節 |
| --- | --- | --- |
| Subject | `Documents/Subject/__Documents_SubjectA/README.md` | `## 企画内容`、`## 企画実装`（Achievement）、`## 企画構想`（Schema） |
| Achievement | `Documents/Achievement/__SubjectA_AchievementA/README.md` | `## 実装内容`、`## 実装証拠`（Evidence）、`## 実装手順`（Todo）、`## 実装構想`（Schema） |
| Evidence | `Documents/Evidence/__AchievementA_EvidenceA/README.md` | `## 証拠内容`、`## 結果区分(正常値/異常値)`、`## 証拠結果`（Result）、`## 証拠手順`（Todo）、`## 証拠構想`（Schema） |
| Result | `Documents/Result/__EvidenceA_ResultA/README.md` | `## 引数`、`## 表明`、`## 記録一覧`（Record） |
| Record | `Documents/Record/__ResultA_20001010101010/README.md` | `## 確認日(yyyy-MM-dd HH:mm:ss)`、`## 確認者`、`## 判定(OK/NG)`、`## 記録内容` |
| Todo | `Documents/Todo/__AchievementA_TodoA/README.md` | タイトル直下に、実装操作だけを番号付きで記載する。独自の見出しは追加しない。 |
| Schema | `Documents/Schema/__SubjectA_SchemaA/README.md` | `## 体験`、`## 評価`、`## 仮説`、`## 抽象目標`、`## 実行目標` |

`Document` と `Group` には現時点で `__*A` ひな型が存在しない。この 2 タイプの新規 README を作成する必要がある場合は、ひな型を先に追加するか、記載内容を確認してから作成する。

`Evidence` の `結果区分(正常値/異常値)` には、証拠が対象とする確認ケースを `正常値` または `異常値` で記載する。`Result` の `引数` は `- <型> <キー> = <値>`、`表明` は `- <判定種別>(<対象>, <型> <期待値>)` の箇条書きで記載する。`Record` の `判定(OK/NG)` には `OK` または `NG` を記載する。作成時点で子要素がない一覧節には `未記載` を記載する。

### 一覧項目の粒度

一覧ページのリンクは、**1リンクにつき1つの実装タスク**とする。複数の独立した画面部品、利用者操作、または状態遷移を、1つのリンク先READMEにまとめてはならない。

たとえば、基本画面の配置とメニューバーの配置、読込と保存、元に戻すとやり直す、ペインの分割とアクティブペインの切替は、それぞれ別の一覧項目として作成する。保存については、自動保存、手動保存、名前を付けて保存のように起点または振る舞いが異なる操作も分ける。種別ごとに固有項目が異なる画面は、種別ごとに別の一覧項目として作成する。

1つのタスクのREADMEには、そのタスクの目的、対象、完了時の振る舞いだけを記載する。前提となる画面部品や共通状態に触れることはできるが、別タスクの実装を担当範囲として含めない。

### Todo の具体化規約

Todo は、後続の実装担当者が本文の順番どおりに編集すれば対象を実装できる作業手順とする。設計意図だけを述べる抽象的な文（例: 「責務を定義する」や「利用できることを確認する」）だけで終えてはならない。

対象の実装ファイルが存在する場合は、そのファイルを正として読み、実装済みのクラス名・namespace・型・メソッド名・アクセス修飾子・引数・戻り値・固定値・null 時の扱いを手順へ転記する。推測で API 名や値を作らない。

各手順には、必要に応じて次を明記する。

1. 編集するファイルのリポジトリ相対パス、および namespace。
2. 追加または変更するクラス・プロパティ・メソッド・コンストラクタの完全な宣言。
3. メソッド本体で設定・返却する値、分岐、コレクション操作の具体的な式。
4. 複数の値を初期化する場合の設定順序と、固定値・既定値・null 時の値。

Todo には、テスト実行、成功・失敗の判定、期待値との比較、または「確認する」という検証作業を書かない。これらは Evidence、Result、Record に記載する。Todo の末尾は実装操作で終える。

## 生成手順

1. 親 `README.md` を読み、依頼された「○○の一覧」に対応する節を特定する。
2. 要求を1リンクにつき1つの実装タスクへ分解し、既存項目と重複しない表示名・フォルダ名を決める。複数の操作や画面部品を含む項目は、この時点で別項目に分ける。フォルダ名は接頭辞を 1 つ外し、飛ぶ先の名前を半角英数字で付与する。
3. 作成する要素タイプの `__*A` ひな型を読み、規約のフォルダ名でリンク先ディレクトリを作成して、ひな型どおりの `README.md` を記載する。
4. 親 `README.md` の該当節に、規約どおりの `[表示名](相対パス)` のリンク行を追加する。
5. リンク先の存在、相対パス、見出し、必須項目を検査する。

既存の一覧を修正する場合も、リンク先を残したまま表示名だけを変更しない。名称を変更するなら、フォルダ名・リンク・`README.md` のタイトルを同じ作業で整合させる。

## 完了条件

次をすべて満たしたとき、一覧作成は完了とする。

- 依頼された一覧の各項目が、`[表示名](...)` だけのリンク行として親 `README.md` に存在する。
- 各リンク先が `../../<要素タイプ>/<接頭辞を外した現在のフォルダ名>_<飛ぶ先のフォルダ名>/README.md` の形式で、実在する `README.md` を指す。
- 飛ぶ先のフォルダ名が半角英数字のみであり、上位要素の接頭辞が重複していない。
- 新規に作成した各 `README.md` が、要素タイプに対応する必須の内容・節を持つ。
- 親子関係が「許可する親子関係」に適合し、`Group` は横断的なリンク集として扱われている。
- 新規・変更したリンクにリンク切れがない。
- 各リンク先が1つの実装タスクだけを対象とし、独立した画面部品、操作、状態遷移をまとめていない。
