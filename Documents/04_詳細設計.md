# FactStatus 詳細設計・実装手順

## 進め方

各工程は「仕様確認 → 実装 → 自動テスト → 手動確認 → 達成内容一覧の更新」の順で実施する。データ形式を変更する工程では、作業前に `Documents/` をコピーして退避する。

## 1. 環境とベースラインの確認

1. `00_環境構築.md` のコマンドで restore、build、test、UI起動を実行する。
2. 使用SDK、実行したコマンド、失敗内容を記録する。
3. 既存の `Documents/IDPatternRules.json` と `Documents/RelationalData.json` を読み、サンプルデータの構造を確認する。
4. 成功した項目を `03_達成内容一覧.md` の「完了」に更新する。

完了条件: ビルド・テスト・UI起動の可否と、失敗した場合の再現手順が明確であること。

## 2. ドメインルールの確定

1. 各 `IdTypeEnum` の必須属性と作成可能な親を `IDPatternRules.json` と照合する。
2. `CreateEntity`、`DeleteEntity`、`MoveEntity`、`CopyEntity`、`GroupEntity` の事前条件・事後条件をテストケースとして列挙する。
3. 不正なID種別、存在しないID、循環する親子関係、重複グループ登録の扱いを決める。
4. `FactStatusPolicy` と `FactStatusAggregate` に検証を実装し、例外メッセージを利用者が判断できる内容にそろえる。
5. 正常系・異常系のxUnitテストを追加する。

完了条件: 操作ごとの制約がテストで表現され、制約違反時にデータが部分更新されないこと。

## 3. SQLite永続化の実装

SQLiteをFactStatusの必須永続ストレージとする。`FactStatusMain` と `FactStatusAggregate` は、編集対象のエンティティ・関連・選択状態をメモリ上で管理する。SQLiteはそのスナップショットを保存し、起動時に復元する責務だけを持つ。UIからSQLiteを直接呼び出さない。

```text
FactStatus.Desktop
  → FactStatusMain（メモリ上の操作窓口）
  → FactStatusPolicy
  → IFactStatusSqliteRepository（永続化の抽象）
  → FactStatusSqliteRepository
  → SQLite
```

### 3.1 SQLite Repositoryの呼び出し関数

SQLite固有の実装は `FactStatus.Infrastructure.Sqlite` に置き、ドメイン側はRepositoryの抽象のみを参照する。Aggregate全体を保存・復元する永続化操作に加え、SQLite、JSON、XMLの各Repositoryが共通して使用するエンティティ操作およびファイル入出力操作を定義する。

| 関数 | 呼出元 | 戻り値 | 責務 |
| --- | --- | --- | --- |
| `InitializeAsync(CancellationToken)` | 起動時の `FactStatusMain` | `Task` | DBファイル・テーブル・索引を作成し、スキーマバージョンを確認／移行する。 |
| `HasDataAsync(CancellationToken)` | `LoadSqliteAsync` | `Task<bool>` | 保存済みのDocumentがあるかを確認する。 |
| `LoadAsync(CancellationToken)` | `FactStatusMain.LoadSqliteAsync` | `Task<FactStatusAggregate?>` | 全エンティティと親子・グループ関連を読み出し、1個のAggregateとして復元する。データがない場合は `null` を返す。 |
| `SaveAsync(FactStatusAggregate, CancellationToken)` | `FactStatusMain.SaveSqliteAsync` | `Task` | 現在のAggregate全体を単一トランザクションで保存する。失敗時はロールバックし、既存の保存内容を壊さない。 |

### 3.1.1 SQLite / JSON / XML Repository共通関数

以下の関数はSQLite、JSON、XMLの各Repositoryで使用する。型名はドメイン層の `IdValue`、`IdTypeEnum`、`PathValue`、`BoolValue` を用いる。`AddValue` は `pathName`、`title`、`IdType`、`destinationId` を、`PairIdValue` は `targetId`、`destinationId` を保持する値オブジェクトとする。

| 分類 | 関数 | 責務 |
| --- | --- | --- |
| 参照 | `FindById(IdValue id)` | 指定IDのエンティティを取得する。 |
| 参照 | `HasById(IdValue id)` | 指定IDのエンティティが存在するかを判定する。 |
| 参照 | `GetEntityList(IdTypeEnum idType)` | 指定ID種別のエンティティ一覧を取得する。 |
| 参照 | `EntityCount(IdTypeEnum idType)` | 指定ID種別のエンティティ数を取得する。 |
| 集計 | `OKCount()` | OK状態のエンティティ数を取得する。 |
| 集計 | `NGCount()` | NG状態のエンティティ数を取得する。 |
| 検索 | `SearchByTitle(string title)` | タイトルを条件にエンティティを検索する。 |
| 検索 | `SearchByText(string text)` | 本文・説明を条件にエンティティを検索する。 |
| 追加 | `AddEntity(AddValue addValue)` | 1件のエンティティを追加し、`destinationId` に関連付ける。 |
| 追加 | `AddByAddValueList(List<AddValue> addValueList)` | 複数のエンティティを一括追加する。 |
| 移動 | `Move(PairIdValue pairId, bool only)` | `targetId` を `destinationId` へ移動する。`only` は対象のみを操作するかを指定する。 |
| 移動 | `MoveByPairIdValueList(List<PairIdValue> pairIds, bool only)` | 複数の移動を一括実行する。 |
| 複製 | `Copy(PairIdValue pairId, bool only)` | `targetId` を `destinationId` 配下へ複製する。`only` は対象のみを複製するかを指定する。 |
| 複製 | `CopyByPairIdValueList(List<PairIdValue> pairIds, BoolValue only)` | 複数の複製を一括実行する。 |
| 削除 | `Delete(IdValue id, BoolValue only)` | 指定エンティティを削除する。`only` は対象のみを削除するかを指定する。 |
| 削除 | `DeleteByIdValueList(List<IdValue> ids, BoolValue only)` | 複数のエンティティを一括削除する。 |
| 更新 | `UpdateByAttributeId()` | 属性IDを基準に対象エンティティを更新する。 |
| 更新 | `UpdateByAttributeIdList()` | 複数の属性IDを基準に対象エンティティを一括更新する。 |
| 追加 | `AddByPairIdValue()` | IDの組を指定してエンティティまたは関連を追加する。 |
| 追加 | `AddByPairIdValueList()` | 複数のIDの組を指定してエンティティまたは関連を一括追加する。 |
| JSON | `LoadJson(PathValue pathName)` | JSONファイルからデータを読み込む。 |
| JSON | `SaveJson(PathValue pathName)` | 現在のデータをJSONファイルへ保存する。 |
| XML | `LoadXml(PathValue pathName)` | XMLファイルからデータを読み込む。 |
| XML | `SaveXml(PathValue pathName)` | 現在のデータをXMLファイルへ保存する。 |

`Move`、`Copy`、`Delete`、各一括操作、および属性・関連の更新は、Repository実装内で全件を単一の処理単位として扱う。SQLiteではトランザクション、JSON/XMLでは一時ファイルへの出力後の置換を用い、失敗時に中途半端な更新を残さない。

### 3.1.2 Markdown Repository関数

Markdown入出力には次の関数を使用する。

| 関数 | 責務 |
| --- | --- |
| `LoadMarkdown(PathValue pathName)` | 単一のMarkdownファイルを読み込む。 |
| `LoadMarkdownEntitys(PathValue pathName)` | エンティティを表すMarkdown群を読み込む。 |
| `LoadMarkdownDocuments(PathValue pathName)` | Documentを表すMarkdown群を読み込む。 |
| `SaveMarkdown(PathValue pathName)` | 単一のMarkdownファイルへ保存する。 |
| `SaveMarkdownEntitys(PathValue pathName)` | エンティティをMarkdown群として保存する。 |
| `SaveMarkdownDocuments(PathValue pathName)` | DocumentをMarkdown群として保存する。 |

`FactStatusMain` には、UIが呼び出す次の非同期操作を追加する。`LoadSqliteAsync` は `LoadAsync` の結果でメモリ上のAggregateを置き換え、`SaveSqliteAsync` は現在のAggregateを保存する。作成・編集・削除・移動・複製・グループ化は従来どおりメモリ上で完結させ、利用者の保存操作時だけ `SaveSqliteAsync` を呼ぶ。

```csharp
Task LoadSqliteAsync(CancellationToken cancellationToken = default);
Task SaveSqliteAsync(CancellationToken cancellationToken = default);
```

### 3.2 SQLiteの保存単位と整合性

- DBファイルの場所はアプリケーション設定で1つ指定し、接続文字列の生成はRepository実装に閉じ込める。
- `Document`、各エンティティ、`Argument`、`Assertion`、親子リンク、グループメンバーを別テーブルで保存する。エンティティ固有の可変属性は `PayloadJson` 列に保存する。
- エンティティIDは主キー、親子リンクとグループメンバーは複合主キーと外部キーを使う。リンク先のないデータは読込エラーとする。
- `SaveAsync` は削除・挿入またはUPSERTをトランザクション内で実行する。DBへの部分反映は禁止する。
- `LoadAsync` 後は、ID重複・参照先不存在・循環関係を `FactStatusPolicy` で検証してから `FactStatusMain` に設定する。

### 3.3 実装・テスト手順

1. `Microsoft.Data.Sqlite` を追加し、DBファイル作成とスキーマ初期化を実装する。
2. `IFactStatusSqliteRepository` と `FactStatusSqliteRepository` に上記4関数を実装する。
3. `FactStatusMain.LoadSqliteAsync` / `SaveSqliteAsync` を追加し、UIの「開く」「保存」操作から呼び出す。
4. 空DB、保存→読込の往復、リンクを含むAggregate、トランザクション失敗時のロールバック、破損DBの各テストを追加する。

完了条件: SQLiteに保存したAggregateを再起動後に読み込み、エンティティ・属性・親子リンク・グループリンクが同一に復元されること。

## 4. JSON入出力の完成

1. `JsonDto` / `JsonDtoBuilder` が全エンティティ、属性、親子リンク、グループリンクを変換することを確認する。
2. JSON保存 → JSON読込 → 再保存の往復テストを追加する。
3. リレーショナル形式JSONについても同じ往復テストを追加する。
4. ファイル不存在、形式不正、ID重複、参照先不存在のエラーを検証する。
5. 形式を変更する場合は互換性方針と移行手順を記録する。

完了条件: サンプルデータを読み込み、内容と関連を保ったまま保存・再読み込みできること。

## 5. Markdown入出力の完成

1. 各エンティティのMarkdown表現を決める。最低限、ID、タイトル、説明、固有属性、親子リンク、グループリンクを表現する。
2. `MarkdownDtoBuilder` が上記のMarkdownを生成するようにする。
3. `MarkdownRepository.LoadMarkdown` を実装し、単体ファイルをDTOへ変換する。
4. ルート配下を再帰走査して、Markdownツリーから `FactStatusAggregate` を復元する処理を実装する。
5. ファイル名、相対リンク、ディレクトリ名の規約を定義し、Windowsパスと区切り文字の違いを吸収する。
6. 単体・ルート・往復のテストを追加し、既存の `Documents/` サンプルで手動確認する。

完了条件: Markdownツリーの保存と読み込みを往復して、エンティティと関連が復元されること。

## 6. Avalonia UI の実装

1. `IFactStatus` / `IFactStatusCrafter` を通じてUIがドメイン層を呼び出せるようにし、DIの構成を決める。
2. メイン画面を「ファイル操作」「ツリー」「詳細」「操作・集計」の4領域に分ける。
3. ツリーにDocumentからの親子構造を表示し、選択IDを `FactStatusMain.SelectIdValue` に反映する。
4. 選択要素に応じた編集フォームを表示し、作成・編集・削除・移動・複製・グループ化を実装する。
5. 読み込み・保存先の選択、未保存変更の確認、例外メッセージの通知を実装する。
6. 成功・失敗件数と失敗内容を表示する集計ビューを追加する。

完了条件: 利用者がUIだけでサンプルを読み込み、編集し、保存して再度開けること。

## 7. テストと受入確認

1. ドメイン、JSON、Markdown、UIの主要シナリオをテスト一覧にする。
2. テストを実行し、失敗は原因・対応・再実行結果を記録する。
3. 以下を手動受入確認する。

   - 新しいSubjectからAchievement、Evidence、Result、Recordを作成できる
   - EvidenceとRecordの成功／失敗を設定し、集計が変化する
   - Todo、Schema、Groupを作成し、関連を参照できる
   - JSONとMarkdownで保存後に再読み込みできる
   - 不正な操作で既存データが壊れない

4. 残課題と既知の制約を `03_達成内容一覧.md` に更新する。

完了条件: 主要シナリオの自動テストと手動受入確認が完了し、残課題が明文化されていること。
